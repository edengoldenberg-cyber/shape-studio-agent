## 2. The explanation and what a review is about

- Home tab "איך זה עובד": the seven steps, what Claude decides / what the worker does and measures / what Dana checks /
  what nobody checks, and every capability as active, partial or missing. The worker reports what its own machine has
  (content model, face detection, HyperFrames) when it connects; the page shows that, not an assumption.
- Every package: `review_provenance` (sha256 of the file the review looked at, when, how many rounds). The page shows
  which version was reviewed, when, whether it was the final file after all changes, how many criteria were measured /
  seen in stills / assessed by a model / not checked, and the skill versions and references used.
- A review is marked "not current" when: it belongs to another version than the current one, a caption correction was
  saved after it, the post caption was edited after it, or the stored file differs from the reviewed one.
- A rating is information. Nothing approves, publishes or skips a check because of it.

## 3. The editing-skill library (`services/dana_skills.js`, `dana_pipeline/skillgen.py`)

Built on the existing references, profiles and the job's `profile` channel.

- **From analysis** (deterministic): the owner picks findings and numbers of analysed references. Every rule keeps its
  reference, aspect, observation and example times, and how well founded it is.
- **From instructions**: free text, structured by a tool-free model call on the editing computer into rules (with an
  area and an "executable" flag), parameters inside fixed limits, review criteria and contradictions with a proposed
  resolution. May be combined with reference findings.
- A hypothesis is not a rule until the owner adopts it. A rule in an area the worker cannot do (styled transitions,
  music, sound effects, B-roll, anything that is not editing) is kept, marked unsupported, and never applied.
- A draft is never used by a project and never a default. An approved version is immutable; an edit opens a new draft
  version. A project keeps the version it chose. Approving a skill is not an approval to publish.
- Files per version, in the existing skill shape: `SKILL.md`, `profile.json`, `criteria.json`.
- In a project: the approved default, a chosen skill, "let Dana suggest" (among approved skills only, with a reason),
  or none. Applying a skill to an existing project makes a new version and drops the approval.
- In the worker: rules → planner and caption editor; parameters → renderer; rules + criteria → reviewer. The package
  carries `skill_report`: every rule as applied / not followed / not applicable / unsupported / not checked.

Limits seen in these runs:
- "applied / not followed" for a text rule is a model's reading of the transcript, the cards and stills. It is not a
  measurement, and in run A a third of the rules could not be judged that way.
- A skill from analysis carries the reference's own rule texts; several were written for that reference's content and
  simply do not fit another recording (the 4 "not followed" in run A). The draft is meant to be edited before approval.
- "no zooms" was followed because the planner obeyed the instruction; nothing in code forbids a zoom on such a rule.
- The edited clips still have open review items (caption text differences) — they are test outputs, not approved videos.
